# foundation: vision

## Why this exists

Go's standard library makes a set of compromises so that it stays simple to learn and runs the same way everywhere. The API is frozen by the Go 1 promise. Code has to work on every CPU Go supports, so it cannot lean on SIMD or tune for one cache layout. Most functions have one signature that suits everybody, and allocating on the heap is considered a fair price for a friendlier API. For most Go programs that is the right deal.

My projects are not most programs. They are gateways, storage engines and wire codecs, and for them the same compromises show up as allocations on hot paths and cycles left on the table. `foundation` is the standard library with those compromises reversed. Think of it as stdlib v2.0, written for my own systems work.

What it costs, and what it buys:

| Standard library compromise | What foundation does instead | What you pay |
| :--- | :--- | :--- |
| API frozen forever | Changes freely before v1; breaking changes go in the CHANGELOG | Consumers pin a release and upgrade on purpose |
| Same code on every platform | SIMD, assembly generated by `c2plan9`, Go 1.27 intrinsics | amd64 and arm64 on Linux, Windows and macOS come first |
| One signature fits all | `Append*` and `dst []byte` variants, push iterators, specialised types | More packages and a larger surface |
| Allocation is acceptable | Zero-allocation contracts, off-heap memory, explicit ownership (`borrow`) | Callers hand in buffers and manage lifetimes |
| Wait years for new features | Use new Go features as soon as they ship | Needs Go 1.27 (`go.mod`) and `GOEXPERIMENT=simd` |

Every package states which compromise it rejects and what that costs, in its own `doc.go` (see [ADR-0008](adr/0008-doc-go-canonical-truth.md)). A package that cannot fill in that block does not belong here.

## Who uses it

Six projects of mine depend on `foundation`. Each package is supposed to be needed by at least one of them.

| Project | What it is | Foundation packages it leans on most |
| :--- | :--- | :--- |
| `aoni` | Network protocol stack and HTTP client | `silicon/bytesconv`, `silicon/pool`, `iokit`, `codec/json`, `borrow`, `net/quic`, `net/urlkit`, `async/ctxkit` |
| `mach` | Protocol engines (HTTP/1.1, HTTP/2, HTTP/3, HPACK, QPACK) used by `aoni` and `sein` | `silicon/bytesconv`, `silicon/pool`, `silicon/simd`, `borrow`, `net/quic`, `encoding/varint` |
| `sein` | Server network stack and web framework | `net/quic`, `encoding/varint`, `silicon/endian`, `timekit`, `types/uuid`, `async/logkit` |
| `g-man` | Steam client SDK and automation framework | `async/logkit`, `async/event`, `async/fsm`, `async/lifecycle`, `async/rate`, `codec/json` |
| `dawn` | Database protocol drivers and data access layer | `silicon/endian`, `silicon/bytesconv`, `silicon/simd`, `bufkit` |
| `seal` | Fault-tolerant archive and container format (EON) | `codec/compress/*`, `codec/filter/*`, `crypto/*`, `bufkit`, `fskit`, `pathkit`, `argkit`, `tuikit` |

All of them also use `generic` and the `testing/*` helpers. The table comes from their imports and READMEs and lives only here. A package that no project imports needs a reason to stay.

## What belongs here, and what does not

In: building blocks that know nothing about any one product: memory, concurrency, data structures, codecs, cryptography, and transport up to L4 and QUIC.

Out:

- Application protocols (HTTP/1.1, HTTP/2, HTTP/3, HPACK, QPACK, WebSocket, gRPC, the Steam protocol). They live in `mach` or in the project that needs them. See [ADR-0006](adr/0006-l7-boundary-and-mach.md).
- Application logic: domain models, ORMs, query builders, database drivers.
- UI. `tuikit` is for developer tools in a terminal and nothing more.
- Convenience that hides an allocation on a hot path.

## How the code is organised

The rules are short and each has one home:

- Layers and who may import whom: [ADR-0002](adr/0002-layering-and-isolation.md), checked by `root_test.go`.
- Allocation tiers (`zero`, `amortized`, `bounded(N/op)`, `unconstrained`): [ADR-0003](adr/0003-allocation-budgets.md).
- Package documentation lives in `doc.go` and `example_test.go`: [ADR-0008](adr/0008-doc-go-canonical-truth.md).
- Changes go through a pull request with a green CI: [ADR-0009](adr/0009-pr-release-lifecycle.md).
- Coverage may go up but never down: [ADR-0007](adr/0007-coverage-ratchet.md).

`docs/` holds only repository-wide material: this file, [ARCHITECTURE.md](ARCHITECTURE.md) and the ADRs. API documentation is in the packages themselves; read it with `go doc` or on pkg.go.dev.
